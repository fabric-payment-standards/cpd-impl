One payment interface. Any payment rail.

CPD is an open canonical representation for payment intent. Define a payment once, then encode, transport, and route it through whichever payment rail actually settles it — SEPA, cards, a stablecoin network, or something that doesn't exist yet.

Why this exists

Payment rails are proliferating. Payment interfaces should not.

Merchants, fintechs, wallets, processors, and platforms increasingly deal with multiple settlement mechanisms, while users still expect one coherent payment experience. Every new rail tends to bring its own object shape, its own state machine, its own edge cases — and every system integrating it has to learn them from scratch.

01

The rail should be replaceable

CPD-001 separates payment semantics — who, what, how much, under what authorization — from how the value actually moves. Swap the rail; the interface above it doesn't change.

02

It's a model, not a platform

There's no account to create, no service to depend on. `Payment.create()` runs entirely locally. The REST layer in this repository is a convenience, not a requirement.

03

Precision is not optional

Monetary values are decimal strings end to end — never a floating-point `number` — because CPD-001 places no bound on the precision a settlement rail might require.

Architecture

Payment definition, transport, and settlement are three different layers.

CPD-001 occupies the top layer only. This repository implements that layer plus one reference transport codec — everything below "Rail adapter" is intentionally out of scope.

Payment intent
      │
      ▼
   CPD-001                  (canonical semantics — this package: src/cpd)
      │
      ├──── REST / JSON      (this package: src/http)
      ├──── Compact / QR     (FPSF-SS-005 / CPRE — a sibling, specialized codec)
      └──── Other codecs
      │
      ▼
Rail adapter                 (not part of this package)
      │
      ▼
Settlement                   (SEPA, cards, the Stablecoin Stack, ...)
The payment rail should be replaceable without rewriting the payment interface.
Quickstart

From zero to a validated canonical payment.

Use the library directly in TypeScript, or talk to the reference codec server over REST. Both take about the same amount of code.

TypeScript
REST

1. Install

npm install

2. Construct, validate, and transition a Payment

import { Payment, PaymentState } from "@fpsf/cpd";

const payment = Payment.create({
  id: "pay_9f2c1e7a",
  payer: { id: "acct:payer-042", roles: ["payer"] },
  payee: { id: "acct:payee-777", roles: ["payee"] },
  value: { amount: "12.50", asset: "USD" },
  intent: { reference: "invoice-4471" },
  authorization: { method: "signature", data: { sig: "3045..." } },
  state: PaymentState.CREATED,
});

payment.validate();                 // throws CpdValidationError on any violation
const authorized = payment.authorize({ method: "signature", data: { sig: "3046..." } });
console.log(authorized.state);      // "AUTHORIZED"

3. Encode it for transport

import { encode, decode } from "@fpsf/cpd";

const { payload } = encode(payment);
const restored = decode(payload);   // throws on tampering, truncation, or invalid data

1. Run the reference server

npm run dev
# @fpsf/cpd reference server listening on http://localhost:8787

2. Submit a candidate payment

curl -s -X POST http://localhost:8787/v1/payments \
  -H "Content-Type: application/json" \
  -d '{
    "id": "pay_9f2c1e7a",
    "payer": { "id": "acct:payer-042", "roles": ["payer"] },
    "payee": { "id": "acct:payee-777", "roles": ["payee"] },
    "value": { "amount": "12.50", "asset": "USD" },
    "intent": { "reference": "invoice-4471" },
    "authorization": { "method": "signature", "data": { "sig": "3045..." } },
    "state": "CREATED"
  }'

# → { "payment": { ... canonical fields ... }, "valid": true }

3. Encode, transport, decode

curl -s -X POST http://localhost:8787/v1/payments/encode -d '{ "...": "same body" }'
# → { "encoding": "cpd-json-v1", "payload": "eyJhdXRo...", "length": 282 }

curl -s -X POST http://localhost:8787/v1/payments/decode \
  -d '{ "payload": "eyJhdXRo..." }'
# → { "payment": { ... } }

CPD does not settle the transaction — it only carries the intent. What happens after decode is your rail adapter's job.

The smallest possible payment

Six fields. Nothing implicit.

{
  "id": "pay_9f2c1e7a",
  "payer": { "id": "acct:payer-042", "roles": ["payer"] },
  "payee": { "id": "acct:payee-777", "roles": ["payee"] },
  "value": { "amount": "12.50", "asset": "USD" },
  "intent": {},
  "authorization": { "method": "signature", "data": {} },
  "state": "CREATED"
}

Every field here corresponds directly to a field defined in CPD-001 §3. No renaming, no undocumented defaults.

Scope

What CPD does — and doesn't.

CPD does

  • Define canonical payment semantics
  • Normalize payment information
  • Provide an interoperable representation
  • Provide codec boundaries for transport
  • Let downstream systems choose their settlement rail

CPD does not

  • Custody funds
  • Settle transactions
  • Operate a payment network
  • Replace wallets, banks, or card networks
  • Determine which rail must be used
Where this gets used

If your system accepts more than one payment rail, CPD gives those rails a common interface.

CPD does not perform routing itself — it gives the systems that do routing a shared representation to route on top of.

Checkout & point-of-saleOne payment shape across every accepted rail.
Invoicing & B2B billingNormalize payment intent before it hits your ledger.
Cross-border paymentsRepresent intent independently of which corridor settles it.
Payment orchestrationRoute the same canonical object across multiple processors.
Fintech platforms & walletsNormalize inbound payment data from many sources.
Marketplace payoutsReconcile payouts across settlement mechanisms.
Recurring payment requestsRepresent a request independently of the eventual rail.
Multi-rail routingGive a routing engine one object shape to reason about.
Specialized codecs

CPD is the semantic layer. Codecs sit on top of it.

CPD-001
  canonical payment semantics
       │
       ├── REST / JSON codec           (this package)
       │
       └── CPRE / FPSF-SS-005
             Cryptocurrency payment request encoding —
             a compact, QR-optimized binary format for
             crypto-settled payment requests within the
             Stablecoin Stack.
FPSF-SS-005 is a specialized crypto-payment-request representation — a sibling codec built for a specific transport (QR, offline-shareable), not the parent concept. This package does not depend on it, and it does not depend on this package.
Before you ship

The integration checklist.

CPD objects validate successfully. — checked via Payment.create or Payment.check.
Monetary values stay decimal strings end to end. — never coerced to a floating-point number.
Canonical serialization is deterministic in your usage. — via canonicalJSON, not ad hoc JSON.stringify.
Errors are surfaced explicitly. — not swallowed or silently coerced into a default.
Settlement logic lives outside the CPD layer. — in your rail adapter, not in this package.
Your rail adapter consumes payment.toJSON(). — the canonical representation, not internal implementation details.
Round-trip encode/decode tests pass. — for the payloads you actually send: npm test.
State transitions follow the CPD-001 transition graph. — no direct writes to state outside authorize / submit / settle / fail / cancel.
